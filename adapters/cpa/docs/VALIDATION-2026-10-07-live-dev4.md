## 样本范围与关联方法

原生 ECPA `usage_inbox` 中当前可按这两个 session 精确定位的记录始于 10 月 7 日 15:52 / 15:53。
统计固定截止于 **16:28:20 已完成的上游轮次**，使用开始时间加 latency 判定完成时间；
截止时仍在生成的轮次不计入，避免把在途请求当作缺失回答。
不能把这个保留窗口表述为安装后近两天的完整零故障验收。

1. 以原生用量消息的 session 标识限定两个聊天，用消息哈希去重；不将重复 inbox 记录与 usage 表交叉连接。
2. WS 的 request ID 可能是连接级标识，不能据相同 request ID 的记录数推算单次续写。
3. 用唯一的首轮输入 token / 缓存 token、完成时间窗和客户端用量记录寻找同次合并输出。
4. 校验 `客户端 reasoning = 各上游轮次 reasoning 之和`；校验最终 output 为保留的历轮 reasoning 加最后一轮 output，
   而不是把已丢弃的暂定文本/工具 token 当作可见输出。
5. 插件日志按唯一的终止时间邻近项及轮数关联，核对 `run_id`、`path`、追加计数、结果及后继 remap。
   这是多证据关联；当前日志没有可直接连接用量行的执行关联键，不能称为显式 request-ID 外键连接。
6. 同时检查现有客户端的工具调用/回传和 `task_complete`，不把 `interceptor_returned` 本身当成送达确认。

- 会话 B 的客户端在 16:22:57 有一次 `turn_aborted`，reason 为 `interrupted`；随后 16:23:02 的上下文改为 Astra。
