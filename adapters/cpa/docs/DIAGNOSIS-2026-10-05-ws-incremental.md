# dev.2 · 续写后的 WebSocket 增量衔接诊断

日期：2026-10-05。CPA / SDK 8.0.13，CodexReflow 0.1.0-dev.2。
本记录仅包含合成响应 ID、虚构凭证和行为摘要，不保存用户提示词、账号、线上响应或加密内容。

## 问题与当前结论

首轮握手、正常回答以及单次 516 续写成功，不代表下一轮增量输入仍可继续。
dev.2 的自动模型选择没有修改原有 response ID 折叠逻辑：客户端始终看到第一轮 ID，
但内部追加调用可能推进上游连接内的最近响应状态。

OpenAI 的 [WebSocket 文档](https://developers.openai.com/api/docs/guides/websocket-mode#how-continuation-works)
说明：响应缓存依赖连接内状态；`store=false` 时没有持久化回退，找不到引用响应可返回
`previous_response_not_found`。隔离测试采用该条件的严格合成缓存，不声称代表所有上游部署。

## 四组隔离对照

运行真实 CPA 8.0.13 和 dev.2 DLL，使用独立端口、空临时认证目录与本地合成 WS 上游。
每个客户端在第一次 `response.completed` 后，通过同一 WS 连接发送引用其 ID 的第二次增量请求。
只修改本地诊断脚本的合成服务，不修改生产服务或插件实现；真实模型调用数为零。

| 插件 | 首轮合成 516 | 首次上游轮数 | 客户端记住的 ID | 第二次请求时上游最近 ID | 第二次结果 |
|---|---|---|---|---|---|
| 关闭 | 否 | 1 | `resp_1` | `resp_1` | 成功 |
| 关闭 | 是 | 1 | `resp_1` | `resp_1` | 成功 |
| 开启 | 否 | 1 | `resp_1` | `resp_1` | 成功 |
| 开启 | 是 | 2 | `resp_1` | `resp_2` | 400，`previous_response_not_found` |

最后一组的内部追加请求携带完整重放输入，不引用父 ID；其响应推进缓存至 `resp_2`。
随后客户端仍引用 `resp_1`，被合成缓存拒绝。所有请求均使用 WS，未发生 HTTP 回退。
四组均符合诊断预期；这不是“四组功能验收全部成功”，其中一组刻意复现了功能失败。
详细合成报告和一次性探针存于忽略目录，未加入发布包。

## 与线上错误的关系及 516 统计限制

线上同码错误与本缺陷高度吻合，但缺少相应每轮响应和后继请求的完整关联抓取，不能声称已经逐包证明每条错误的因果。
另有连接断开、重连、缓存失效等可能路径，应区分错误码本身与诱因。

当前插件为保护上下文，仍不接管携带 `previous_response_id` 的请求。
自动模型选择只解决名称选择，不等于每次 WS 增量生成都经过插件。
上游使用记录按轮次写入，客户端折叠不会删除这些记录；WS 的 request ID 又可被同一连接内的多个生成共用。
因此既不能用 516 的出现证明插件失效，也不能用同一连接下的多条记录证明它追加了调用。

## 当时提出的修复与验收范围

1. 先设计客户端可见合成响应与上游真实最近响应的上下文衔接，不能只改最后一个 ID 而忽略事件和工具历史的一致性。
2. 将“首轮触发续写 → 同连接后继输入”的对照纳入常规回归。
3. 覆盖无续写、多次续写、工具调用及回传、增量文本、完整重放、重连、取消和并发隔离。
4. 增加不含提示词和加密内容的请求级接管/绕过/续写结果证据，再经授权进行少量真实模型验收。

本次仅诊断，没有实现或上线该修复，也没有擅自切换生产 WebSocket 设置。
